TypeScript のプロジェクトが育ってくると、設定オブジェクトや DB クライアント、各種サービスを関数の引数で5階層もバケツリレーするのはすぐに限界が来ます。かといって、テストで依存先を1つ差し替えたいだけなのに、`vi.mock` のようなモジュールモックの黒魔術やクラスデコレータを持ち込むのも大げさですよね。`dn-ioc` は、ごく普通の関数だけで型安全に依存関係を組み立てられる、裏側のマジック一切なしの DI カーネルです。

## 要するにプロバイダはただの関数です

値を返す関数を書けるなら、もう `dn-ioc` の使い方は半分マスターしています。継承すべき基底クラスもなければ、`@Injectable()` のようなわざわざデコレータを書く必要はありません。`tsconfig.json` の `emitDecoratorMetadata` も、`reflect-metadata` のポリフィルも不要です。

すべてのプロバイダは、単なる `(ctx: Context) => T` 型のファクトリ関数です。

- 引数で `{ inject, onDispose }` を受け取り、ほかの依存は `inject()` で取り出して、**任意の TypeScript の値**を返します。オブジェクトリテラル、関数、プリミティブ、クラスインスタンス、`Promise` など何でもOKです。
- `bootstrapApp()` は独立したルートスコープを組み立てて `App` ハンドルを返しますが、この時点ではまだファクトリ関数を1つも実行しません。
- 実際に処理が走り出すのは `await app.start()` を呼んだ瞬間です。上の `minimal.ts` は開いたソケットやタイマー、ファイルハンドルを持っていないので、`app.stop()` すら呼ぶ必要がありません。

<Callout kind="tip" title="ルート関数は「値を返す」のではなく「処理を走らせる」場所">

`bootstrapApp()` に渡す関数の戻り値は `void` または `Promise<void>` に限定されています。計算結果を外に返す関数ではなく、必要な依存を `inject()` してアプリを動かす `main()` エントリポイントだと考えてください。

</Callout>

## 公開 API はたった6つの関数だけ

ランタイムの公開 API は、全部合わせても6つの関数に収まります。この6つの役割さえ押さえてしまえば、隠れた設定レイヤーに悩まされることはありません。

| 関数 | 作るもの | 使いどころ |
| --- | --- | --- |
| `provide(factory, options?)` | `Ref<T>` | 初回の `inject()` で自動登録される具象プロバイダを定義します。 |
| `token<T>(description?)` | `Token<T>` | デフォルト実装を持たない、純粋な型の契約（ポート）を宣言します。 |
| `provideFor(key, factory, options?)` | `ProviderDef<T>` | `Token<T>` に実装を紐づけるか、テストや上書き用に `Ref<T>` を差し替えます。 |
| `bundleProviders(...inputs)` | `ProviderBundle` | 関連するバインドや `Ref` を1つにまとめ、呼び出し側が1行で導入できるようにします。 |
| `isProvideRef(value)` | `value is Ref<unknown>` | 未知の値が `provide()` で作られた本物の `Ref` かどうかを実行時に判定します。 |
| `bootstrapApp(fn, options?)` | `App` | `start()`・`stop()`・`await using` に対応した独立したアプリグラフを組み立てます。 |

## JavaScript が動く場所ならどこでも動く

`dn-ioc` はランタイム依存ゼロで、minify 後わずか `4.8 kB`（gzip なら `1.9 kB`）しかありません。

さらに大事なのが、カーネル内部で **プラットフォーム固有の API に一切触れていない** ことです。`process` も DOM グローバルもタイマーも使いません。まったく同じ依存グラフが Node.js、Bun、Deno、ブラウザ、Web Worker、さらにはサーバーレスやエッジランタイムでもそのまま動きます。終了シグナルの扱い方は実行環境ごとにバラバラなので、カーネル側で勝手に推測したりはしません。必要なときだけ、お使いのランタイムのシグナルやアンマウント処理に `app.stop()` をつなげばOKです（詳しくは [ライフサイクルとクリーンアップ](/ja/lifecycle/) を見てください）。

## あえて入れていない機能

カーネルを小さく保つため、「依存の組み立て」と「アプリの制御フロー」の境界線をはっきり引いています。`dn-ioc` には、次の機能を **あえて入れていません**。

- **デコレータ・リフレクション・グローバルコンテナ:** `bootstrapApp()` を呼ぶたびに完全に独立したグラフが作られるため、並列テストでグローバル状態を取り合って壊れることがありません。
- **フレームワーク特有の儀式:** モジュール専用クラス、組み込みの HTTP リクエストスコープコンテナ、マルチバインディング、OS シグナルの自動購読などは一切ありません。
- **魔法の自動キャンセルやオブジェクト無効化:** `stop()` を呼ぶと以降の `inject()` は閉じられ、登録済みのクリーンアップフックが走りますが、通信中の I/O を勝手に中断したり、`await` されていない野良ファクトリの完了を待ったり、すでに変数に保持している JavaScript オブジェクトを無効化したりはしません。リクエストの受付停止や `AbortController` の配線、グレースフルシャットダウンの順序制御は、すべてあなたの手元でコントロールできます。

<Callout kind="note" title="凍結された不透明ハンドルであり、サンドボックスではありません">

`token()`、`provide()`、`provideFor()`、`bundleProviders()` が返すハンドルは、すべて内部で追跡される `Object.freeze` 済みの不透明オブジェクトです。スプレッド構文などで浅くコピーしたオブジェクト（`{ ...configRef }`）を渡しても、カーネルは偽物として弾きます。なお、`dn-ioc` は信頼できるアプリコードのためのインプロセス DI カーネルであり、悪意あるコードを隔離するセキュリティサンドボックスではありません。

</Callout>
