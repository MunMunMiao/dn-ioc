## 判断基準は「import していい方向かどうか」だけ

`inject()` を呼ぶ側のファイルについて、たった1つだけ質問してみてください。**「このファイルから、具象実装のファイルを直接 `import` しても構わないか？」**

- **YES → `provide()`（`Ref<T>`）を使う:** `Ref` はキーとファクトリ関数を1つのエクスポートにまとめたものです。`user-service.ts` で `userRepositoryRef` を import すれば、`user-repository.ts`（さらにそこが import している `databaseRef`）がそのままモジュールグラフに入ります。Controller が Service を呼び、Service が Repository を呼ぶ王道の **MVC** 構成なら、これがベストです。余計なインターフェース専用ファイルも中央コンテナへの登録作業もいらず、型推論もフルに効きます。
- **NO → `token<T>()`（`Token<T>`）を使う:** `Token` が持つのは TypeScript の型と診断用の名前だけで、実行時の実装コードはゼロです。**DDD / クリーンアーキテクチャ** では、内側の `domain/` 層で `OrderRepository` インターフェースと `orderRepositoryToken` を公開し、外側の `infra/` 層が `domain/` を import して `provideFor()` で SQL 実装を紐づけます。こうすれば、コアなビジネスロジックが DB ドライバや HTTP SDK、`infra/` ディレクトリを import してしまうことは絶対にありません。

また、環境変数の URL や API キー、サブツリーごとの設定値のように、「起動時に外から与えられる値で、そもそもデフォルト実装を書けないもの」にも `token()` がぴったりです。

## トレードオフの比較表

上のファイルツリー（`mvc/` と `ddd/`）の4ファイルを見比べながら、実務上の違いを整理してみましょう。

| 観点 | `Ref<T>`（`provide()`） | `Token<T>`（`token()` + `provideFor()`） |
| --- | --- | --- |
| **コンパイル時の結合** | 使う側が具象モジュールを直接 import する。 | 使う側は契約だけを import し、外側の層が契約を import してバインドする。 |
| **配線のボイラープレート** | ゼロ — アクティブスコープでの初回 `inject()` で自動登録。 | 明示的 — `{ providers }` やバンドル内で `provideFor()` が必須。 |
| **テストでの差し替え** | `provideFor(ref, fakeFactory)` | `provideFor(token, fakeFactory)` — まったく同じ書き方。 |
| **単体テストでモックし忘れたら** | **暗黙フォールバック:** 本物の実装がそのまま組み立てられて動く。 | **即座に失敗:** `start()` が `No provider for token: Name` で reject される。 |
| **エラー時の診断名** | 関数名（`const UserService = ...; provide(UserService)`）、無名なら `<anonymous>`。 | 説明文字列（`token('OrderRepository')`）、省略時は `<anonymous>`。 |
| **向いている場所** | MVC の Controller / Service / Repository、ユースケース、内部ヘルパー。 | DDD のドメインポート、横断的ポート（`Clock`, `Mailer`）、実行時の設定やシークレット。 |

## 1つのコードベースで両方混ぜて使うのが自然です

`Ref` か `Token` かは「リポジトリ全体でどちらか一方に統一しなければならない宗派」ではありません。本番のアプリケーションでは、適材適所で両方を並べて使うのが一番自然です。

- かっちりした DDD のサービスであっても、**アプリケーション層のユースケース**（`orderServiceRef`）や **`infra/` 内部のプライベートなクライアント**（`sqlTableRef`）はただの `Ref` で十分です。これらを呼ぶ側は外側または同じ層にいて、直接 import するのが正しい方向だからです。`token()` が必要なのは、内側の層から外側のアダプタへ矢印を逆転させたい境界ポートだけです。
- シンプルな MVC アプリであっても、実行時にしか決まらない `DatabaseUrl` 文字列や、「単体テストでうっかり本物を叩いたら大事故になる外部決済 API」などにはピンポイントで `token()` を混ぜることができます。

<Callout kind="note" title="アーキテクチャ境界は Linter でも守ろう">

`dn-ioc` が解決するのは実行時のハンドルであり、TypeScript の `import` 文そのものを監視するわけではありません。`domain/` から `infra/` への依存を断つために `Token` を選んだなら、Biome や ESLint の `noRestrictedImports` ルールもセットで入れて、うっかり逆方向の自動 import が混ざったら CI で落とすようにしておくのが鉄板です。

</Callout>
