When you start structuring a real codebase with `dn-ioc`, the first design question you'll hit is whether a dependency should be a `Ref<T>` from `provide()` or a `Token<T>` from `token()`. You don't have to guess or treat it as a matter of style—**module import direction settles the choice every single time.**

## Import Direction Is the Decision Rule

Ask one question about the module calling `inject()`: **is this file allowed to import the concrete implementation?**

- **Yes → use `provide()` (`Ref<T>`):** A `Ref` bundles its key and its factory function into one export. Importing `userRepositoryRef` in `user-service.ts` pulls `user-repository.ts`—and whatever `databaseRef` it imports—straight into your module graph. In a layered **MVC** service where controllers import services and services import repositories, that's exactly what you want: zero extra files, zero central registration boilerplate, and full type inference.
- **No → use `token<T>()` (`Token<T>`):** A `Token` carries only a TypeScript type and an optional diagnostic string—zero runtime code. In **DDD / Clean Architecture**, your inner `domain/` layer defines `OrderRepository` and exports `orderRepositoryToken`, while your outer `infra/` layer imports `domain/` and binds the SQL implementation with `provideFor()`. Your core business logic never imports a database driver, an HTTP SDK, or `infra/`.

Tokens also shine whenever a value only exists at startup—like environment URLs, API credentials, or per-subtree configuration—where there's no sensible default factory to write in the first place.

## Side-by-Side Trade-Offs

Browse the four files in the tree above (`mvc/` vs `ddd/`) against the practical trade-offs below:

| Dimension | `Ref<T>` (`provide()`) | `Token<T>` (`token()` + `provideFor()`) |
| --- | --- | --- |
| **Compile-time coupling** | Consumer imports the concrete module directly. | Consumer imports only the contract; outer layer imports the contract to bind it. |
| **Wiring boilerplate** | Zero—self-installs on first `inject()` in the active scope. | Explicit—must be bound via `provideFor()` in `{ providers }` or a bundle. |
| **Swapping in tests** | `provideFor(ref, fakeFactory)` | `provideFor(token, fakeFactory)` — exact same helper. |
| **Forgotten fake in a unit test** | **Silent fallback:** builds and runs the real implementation. | **Fast failure:** rejects `start()` with `No provider for token: Name`. |
| **Diagnostic name in errors** | Function name (`const UserService = ...; provide(UserService)`), or `<anonymous>`. | Description string (`token('OrderRepository')`), or `<anonymous>`. |
| **Best fit** | MVC controllers, services, repositories, use cases, internal helpers. | DDD domain ports, cross-cutting ports (`Clock`, `Mailer`), runtime config/secrets. |

## Mixing Both in the Same Codebase

Choosing between `Ref` and `Token` isn't a repo-wide religion—most production apps use both right next to each other:

- Even in a strict DDD service, **application use cases** (`orderServiceRef`) and **private infrastructure clients** (`sqlTableRef`) are plain `Ref`s because their callers live in outer or same-tier modules that are meant to import them. Only the boundary ports crossing from inner layers to outer adapters need `token()`.
- Even in a straightforward MVC app, you can reach for `token()` for a runtime `DatabaseUrl` string or a third-party payment gateway you never want unit tests hitting by accident.
