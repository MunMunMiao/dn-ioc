## 用獨立假實作跑單元測試

寫單元測試嗰陣，你只需要開一個專屬嘅 `bootstrapApp()`，然後**淨係裝入**受測目標需要嗰幾個假實作（好似 `order-service.unit.test.ts` 入面嘅 `fakeOrders`、固定時間嘅 `Clock` 同埋 `fakeMailer`）。

無論個 `key` 係 `Token<T>` 定係 `Ref<T>`，`provideFor(key, fakeFactory)` 嘅寫法都完全一樣；**但萬一你唔記得 mock 某個依賴，兩者嘅後果就差好遠：**

| Key 種類 | 單元測試漏寫 `provideFor()` 嗰陣 | 實際影響 |
| --- | --- | --- |
| **`Token<T>`** | `app.start()` 即刻 reject `No provider for token: Name`。 | **即刻 Fail fast：** 單元測試絕對唔可能唔小心連咗去真 socket 或者真係寄咗封電郵出去。 |
| **`Ref<T>`** | 唔當係錯 —— 自動安裝兼執行嗰個 `Ref` 帶住嘅真實 factory。 | **靜默行返真嘢：** 對於純記憶體輔助工具好方便，但如果嗰個漏咗 mock 嘅 `Ref` 會掂外部 I/O 就有風險。 |

你可以將上面份 DDD 單元測試同下面份 MVC 測試（`services/user-service.test.ts`）拍埋一齊睇：用 `provideFor(userRepositoryRef, fakeUserRepository)` 換走 `userRepositoryRef` 一樣咁乾手淨腳，只要你記得將 `userServiceRef` 背後會掂到外部 I/O 嘅 `Ref` 全部換晒做假實作就冇問題。

<Callout kind="tip" title="令測試失敗時嘅錯誤訊息更易睇">

記得幫每個 Token 寫返清楚個介面描述名（例如 `token<Mailer>('Mailer')`），同時幫 `provide()` 嘅 factory 改返個真函式名（例如 `provide(function OrderService({ inject }) { ... })`）。咁樣萬一測試漏綁咗依賴或者唔小心寫出循環依賴，錯誤訊息會直接指明 `OrderService` 同 `Mailer`，唔使對住堆 `<anonymous>` 估餐死。

</Callout>

## 整合測試：喺 Bundle 後面局部覆蓋

單元測試負責驗證業務邏輯配假實作行得通；整合測試就負責驗證真實嘅 SQL Repository、資料序列化同業務 Service 夾埋一齊真係夾得埋，同時將 SMTP 電郵或者 Stripe 扣數呢類外部第三方服務換成假替身。

因為 `dn-ioc` 會按源碼順序由左至右攤平陣列同 `ProviderBundle`，而且**同一個 scope 入面寫喺後面嘅綁定會靜靜雞覆蓋前面嗰個**，你可以先裝入成包正式環境用嘅 `infraProviders`，再緊貼喺佢後面覆蓋單一個 Port：

- **正確次序（`[infraProviders, provideFor(mailerToken, fakeMailer)]`）：** 先裝好 `sqlTableRef`、`sqlOrderRepositoryProvider`、`systemClockProvider` 同 `smtpMailerProvider`，跟住用 `fakeMailer` 換走 `mailerToken`。
- **調轉咗次序（`[provideFor(mailerToken, fakeMailer), infraProviders]`）：** `infraProviders` 喺你個假實作*之後*攤平，結果會無聲無息將 `mailerToken` 蓋返做真實嘅 `smtpMailerProvider`！呢個位千萬要睇清楚次序。

<Callout kind="note" title="喺巢狀子樹入面做局部覆蓋">

喺頂層 `bootstrapApp(..., { providers })` 做嘅覆蓋，會自動對所有住喺 root scope 嘅 service 生效。如果你試過喺某棵子 `{ providers }` 子樹入面覆蓋某個依賴，但用佢嗰個 consumer 一早已經註冊咗喺頂層 root scope，記得要喺子 scope 入面將 consumer 同依賴兩個一齊重新綁定（詳見[作用域與私有子樹](/zh-hant-hk/scopes/)）。

</Callout>

## 用 await using 幫每個測試自動清場

留意吓 `testOrderSubmitUnit()` 同 `testOrderSubmitIntegration()` 入面嗰句 `await using app = bootstrapApp(...)`：

- 因為 `App` 實作咗 `AsyncDisposable`，一離開個測試函式區塊，TypeScript 就會自動幫你 `await app.stop()`——**就算跑到一半某句 `expect()` 斷言爆咗錯都照樣保證執行。**
- `sqlTableRef` 入面登記嘅 `onDispose` hook 會喺測試結束前乖乖跑完，自動閂好連線池、timer 或者臨時測試 server，連 `try / finally` 樣板碼都慳返。

如果你個專案環境暫時未開 `await using`，用傳統嘅 `try { await app.start() } finally { await app.stop() }` 包住測試內容效果完全一樣——而且因為 `app.stop()` 係冪等嘅，就算喺清理階段唔小心 call 多咗次都絕對安全。
