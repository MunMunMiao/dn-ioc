## 쉽게 말해 프로바이더는 그냥 평범한 함수예요

값을 반환하는 함수를 작성할 줄 안다면 이미 `dn-ioc`를 다 배운 거나 마찬가지예요. 상속받아야 할 베이스 클래스도 없고, `@Injectable()`처럼 굳이 데코레이터를 붙일 필요가 없죠. `emitDecoratorMetadata` 컴파일러 옵션이나 `reflect-metadata` 폴리필도 전혀 필요 없어요.

모든 프로바이더는 그저 `(ctx: Context) => T` 형태의 평범한 팩토리 함수예요.

- `{ inject, onDispose }`를 인자로 받아서 다른 의존성은 `inject()`로 꺼내 쓰고, **어떤 TypeScript 값이든** 그대로 반환하면 돼요. 객체 리터럴, 함수, 원시 값, 클래스 인스턴스, `Promise` 모두 상관없어요.
- `bootstrapApp()`은 격리된 루트 스코프를 준비하고 `App` 핸들을 돌려주지만, 이 시점에는 아직 어떤 팩토리 함수도 실행하지 않아요.
- 실제 실행은 `await app.start()`를 호출하는 순간 시작돼요. 위의 `minimal.ts`는 열어 둔 소켓이나 타이머, 파일 핸들이 하나도 없어서 굳이 `app.stop()`을 호출할 필요조차 없답니다.

<Callout kind="tip" title="루트 함수는 값을 돌려주는 게 아니라 앱을 실행하는 곳이에요">

`bootstrapApp()`에 넘기는 함수는 반드시 `void` 또는 `Promise<void>`를 반환해야 해요. 결과값을 계산해서 밖으로 돌려주는 함수가 아니라, 앱에 필요한 의존성을 `inject()`해서 실제 동작을 시작하는 `main()` 진입점이라고 생각하면 이해하기 쉬워요.

</Callout>

## 공개 API는 딱 여섯 개가 전부예요

런타임 공개 API는 함수 여섯 개에 모두 담겨 있어요. 이 여섯 개가 어떻게 맞물리는지만 익히면 더 이상 외워야 할 숨은 설정이 없어요.

| 함수 | 만드는 것 | 언제 쓰나요? |
| --- | --- | --- |
| `provide(factory, options?)` | `Ref<T>` | 첫 `inject()` 시점에 스스로 등록되는 구체 팩토리를 감쌀 때 써요. |
| `token<T>(description?)` | `Token<T>` | 기본 구현체 없이 순수한 타입 계약만 선언할 때 써요. |
| `provideFor(key, factory, options?)` | `ProviderDef<T>` | `Token<T>`에 실제 구현을 연결하거나, 테스트에서 `Ref<T>`를 가짜 구현으로 바꿔 끼울 때 써요. |
| `bundleProviders(...inputs)` | `ProviderBundle` | 관련된 바인딩과 `Ref`들을 하나로 묶어서 한 줄로 등록하게 해 줄 때 써요. |
| `isProvideRef(value)` | `value is Ref<unknown>` | 알 수 없는 값이 `provide()`로 만든 진짜 `Ref`인지 런타임에 확인할 때 써요. |
| `bootstrapApp(fn, options?)` | `App` | `start()`, `stop()`, `await using`을 지원하는 독립된 앱 그래프를 조립할 때 써요. |

## JavaScript가 도는 곳이라면 어디서든 돌아가요

`dn-ioc`는 런타임 의존성이 0개이고, 압축하면 `4.8 kB`(gzip 기준 `1.9 kB`)밖에 되지 않아요.

더 중요한 건 커널이 **플랫폼 전용 API를 단 하나도 건드리지 않는다**는 점이에요. `process`도, DOM 전역 객체도, 타이머도 쓰지 않거든요. 그래서 똑같은 의존성 그래프가 Node.js, Bun, Deno, 브라우저, Web Worker는 물론 서버리스와 엣지 런타임에서도 코드 한 줄 안 고치고 그대로 동작해요. 종료 시그널은 환경마다 생김새가 다 다르기 때문에 커널이 멋대로 추측하지 않아요. 필요할 때 각 런타임의 시그널이나 언마운트 훅에 `app.stop()`만 연결해 주면 돼요(자세한 내용은 [생명주기와 리소스 정리](/ko/lifecycle/)에서 살펴볼게요).

## dn-ioc가 의도적으로 뺀 것들

커널을 작고 단단하게 유지하려면 '의존성 연결'과 '애플리케이션 제어 흐름' 사이에 선을 분명하게 그어야 해요. 그래서 `dn-ioc`는 아래 기능들을 **의도적으로 넣지 않았어요**.

- **데코레이터, 리플렉션, 전역 컨테이너:** `bootstrapApp()`을 호출할 때마다 완전히 독립된 그래프가 만들어지기 때문에, 테스트를 병렬로 돌려도 전역 상태가 꼬일 일이 없어요.
- **프레임워크 특유의 번거로운 격식:** 별도의 모듈 클래스, 내장 HTTP 요청 스코프 컨테이너, 멀티 바인딩, 자동 OS 시그널 리스너 같은 건 없어요.
- **마법 같은 자동 취소나 객체 무효화:** `stop()`을 호출하면 이후의 `inject()` 호출을 막고 등록된 정리 훅을 실행해 주지만, 진행 중인 I/O를 강제로 끊거나 분리된 미완료 팩토리를 기다리거나 이미 변수에 담아 둔 JavaScript 객체를 무효화하지는 않아요. 새 요청 차단, `AbortController` 연결, 우아한 종료(graceful drain) 순서는 온전히 우리 코드가 직접 제어해요.

<Callout kind="note" title="동결된 불투명 핸들이지, 보안 샌드박스는 아니에요">

`token()`, `provide()`, `provideFor()`, `bundleProviders()`가 반환하는 핸들은 모두 내부에서 추적되는 동결(`Object.freeze`) 불투명 객체예요. 전개 연산자로 복사한 객체(`{ ...configRef }`)를 넘기면 커널이 가짜로 판단하고 거부해요. 단, `dn-ioc`는 신뢰할 수 있는 애플리케이션 코드를 위한 인프로세스 커널이지 격리용 보안 샌드박스는 아니에요.

</Callout>
