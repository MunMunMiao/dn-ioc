當核心商業規則的生命週期比眼下使用的 SQL 驅動套件、寄信廠商或 HTTP 框架還要長久時，採用 **DDD / 整潔架構（六角形架構）** 就能把外部底層細節擋在核心領域模型之外。在 `dn-ioc` 裡實作依賴反轉，完全不用寫抽象基礎類別或複雜的容器模組：最內層的 `domain/` 宣告介面與 `token()` 連接埠（port），`application/` 用 `provide()` 編排應用情境（use case），而最外層的 `infra/` 將真實轉接器（adapter）打包成單一一個 `bundleProviders()` 匯出就大功告成。

/>

## 1. 純淨的領域實體與連接埠 Token（domain/）

`domain/` 資料夾位於整張依賴圖的正中心，**完全不匯入專案裡任何其他分層**。除了像 `Order` 這樣的領域實體外，它也負責定義外部世界必須滿足的 **Port（連接埠）**——包含資料持久化儲存庫（`OrderRepository`），以及像系統時間（`Clock`）與寄信服務（`Mailer`）這類橫切關注點的副作用。

每個連接埠都是一組固定搭配：一個 TypeScript `interface`，加上一個直接以該介面命名的 `token<T>('Name')`。把讀取系統時間封裝在 `clockToken` 後面，商業邏輯裡就不會到處直接呼叫 `new Date()`，任何跟時間相關的狀態轉換在測試裡都能做到 100% 穩定可預測。

## 2. 應用層服務（application/）

`application/` 層負責協調領域實體與各個連接埠，完成像 `OrderService.submit(id)` 這樣的應用情境。請特別留意這裡刻意採用的混合設計：

- `OrderService` 取得外部能力時，一律只透過**領域層 Token**（`orderRepositoryToken`、`clockToken`、`mailerToken`）注入——它完全不知道、也不在乎訂單實際上是存在 Postgres、SQLite 還是記憶體裡的 `Map`。
- 然而 `orderServiceRef` 自己卻是透過 `provide(({ inject }) => { ... })` 匯出成一個 **`Ref`**！為什麼？因為會呼叫 `application/` 的角色——像是 HTTP Controller、CLI 指令、佇列 Worker 與測試程式碼——全都位於*更外層*，本來就應該直接往內匯入應用層服務。既然模組匯入箭頭已經指向內側，就完全沒必要再多包一層多餘的 Token。

## 3. 基礎設施轉接器與整層打包（infra/）

`infra/` 資料夾負責匯入 `domain/` 的型別契約，並針對真實的資料庫驅動套件、第三方 SDK 與外部服務撰寫實作：

- **把底層連線控柄留在 `infra/` 內部私有：** 在 `sql-order-repository.ts` 裡，`sqlTableRef` 是一個不對外匯出的內部 `Ref`，負責管理底層資料表／連線池狀態並註冊 `onDispose` 清理掛鉤。`sqlOrderRepositoryProvider` 在幕後注入 `sqlTableRef`，而 `domain/` 與 `application/` 從頭到尾都不必知道 `sqlTableRef` 的存在。
- **將整層轉接器打包進 `infraProviders`：** `infra/providers.ts` 把 `sqlTableRef`（確保根作用域裡所有轉接器共用同一個底層連線客戶端）連同每一個 `provideFor()` 綁定，整合成單一一個 `bundleProviders(...)` 控柄。
- **新增轉接器只需修改兩處：** 日後新增任何基礎設施轉接器時，只需要在 `infra/` 裡面做兩件事——寫好它的 `provideFor()` 綁定，並在 `infraProviders` 多加一行。外部所有的程式進入點完全不用改動。

<Callout kind="caution" title="千萬別把 DDD 轉接器匯出成 Ref 讓 domain 或 application 匯入">

千萬別一時圖方便，在 `infra/` 裡寫出 `export const sqlOrderRepositoryRef = provide(...)` 然後在 `domain/` 或 `application/` 裡反過來匯入它。這麼做不僅會讓核心商業邏輯直接綁死在 SQL 驅動套件上，還會讓匯入箭頭**反向往外指**：因為 `infra/sql-order-repository.ts` 已經從 `domain/order.ts` 匯入了 `Order`，一旦 `domain/` 又反過來匯入 `infra/`，立刻就會產生 ES 模組循環相依（circular dependency）。請讓連接埠維持以 `token()` 放在 `domain/`，並在 `infra/` 用 `provideFor()` 進行綁定。

</Callout>

## 4. 組裝根（Composition Root）與多進入點重用

`main.ts` 就是整個專案的 **Composition Root（組裝根）**——全專案唯一同時匯入 `application/` 與 `infra/`，並透過 `providers: [infraProviders]` 把兩端扣合在一起的地方。

因為 `infraProviders` 是可直接重用的打包物件，而且 `orderServiceRef` 與傳輸協定完全解耦，要在同一個領域核心上開啟多個不同進入點，每個都只要寥寥幾行程式碼：

- **HTTP API 伺服器（`main.ts`）：** 掛載 `[infraProviders]`，並在 `bootstrapApp()` 裡當場呼叫 `inject(orderServiceRef)`（萬一漏綁了任何一個 Token，`await app.start()` 啟動時就會立刻報錯拒絕，不會等到線上客戶結帳到一半才出事），最後交給路由層處理請求。
- **佇列 Worker 或 CLI 批次工具（`worker.ts`）：** 在各自的進入點呼叫 `bootstrapApp(..., { providers: [infraProviders] })` 並注入同一個 `orderServiceRef`——若是執行資料回補腳本不想真的寄信給客戶，只要在 `infraProviders` *後面* 補上一行 `provideFor(mailerToken, dryRunMailer)` 就能原地覆寫寄信服務。
- **純單元測試（`application/order-service.test.ts`）：** 完全不載入 `infraProviders`，只掛載輕量的記憶體 `provideFor()` 測試替身。只要漏綁任何一個連接埠，`unitTestApp.start()` 就會立刻以 `No provider for token: Mailer` 快速失敗。

## 5. 分層匯入邊界速查

由於 `dn-ioc` 只在執行期處理控柄、不會介入靜態 `import` 檢查，平時協作請依下表守住各層目錄的匯入方向：

| 分層目錄 | 允許匯入的專案路徑 | 禁止匯入的專案路徑 |
| --- | --- | --- |
| **`domain/`** | 無（僅可匯入 `'dn-ioc'` 的 `token`） | `application/`、`infra/`、`main.ts` |
| **`application/`** | `domain/` | `infra/`、`main.ts` |
| **`infra/`** | `domain/` | `application/`、`main.ts` |
| **`main.ts`（各進入點）** | `application/`、`infra/`、`domain/` | — |
